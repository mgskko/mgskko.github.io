> **바이브코딩 일대기 번외편** | 풋살 앱 연재를 잠깐 쉬고, 이 블로그 자체를 AI와 대화만으로 갈아엎은 하루를 기록한다. 코드는 한 줄도 직접 치지 않았다. 대신 무엇을 원하는지, 무엇이 마음에 안 드는지를 끝까지 말했다.

## 출발점 — "이게 먼지 앎?"

이 블로그는 원래 **Minimal Mistakes**라는 유명한 Jekyll 테마를 포크해서 만든 것이었다. 글은 197개나 쌓였는데, 화면은 처음 포크했을 때 그대로였다. 누가 봐도 "테마 그대로 가져다 쓴 블로그"였다.

이번에 쓴 도구는 **Claude Code**다. 웹에서 클라우드 세션을 열고 GitHub 저장소(`mgskko.github.io`)를 연결하면, AI가 저장소를 클론해서 파일을 읽고, 고치고, 빌드하고, 커밋하고, PR까지 만든다. 나는 채팅창에 말만 한다.

첫 메시지는 이랬다.

```
이게 먼지 앎?
```

진짜 이게 전부였다. AI는 저장소를 훑어보고 이렇게 정리해 줬다.

- Jekyll + GitHub Pages로 운영하는 개인 공부 블로그
- 테마는 Minimal Mistakes를 포크한 것 (테마 원본의 `docs/`, `test/`, `CHANGELOG.md`가 그대로 남아 있음)
- `_posts/`에 글 약 197개, 주제별 폴더로 나뉨
- 커밋 메시지가 `0408`, `0407`처럼 날짜로만 되어 있음
- `README.md` 내용이 `hi` 한 줄

내 블로그를 나보다 더 정확하게 요약했다. 여기서부터 하루짜리 리뉴얼이 시작됐다.

## 1단계 — 글부터 하나 써보기

리뉴얼 전에 먼저 글을 하나 써 달라고 했다.

```
블로그 내용 추가하고 싶음 데이터 운영에 관해서
```

AI가 바로 쓰지 않고 **객관식으로 두 가지를 물어봤다.**

- 어떤 내용으로 쓸까? (개념 정리 / 내 업무 경험 / 툴·실습 중심)
- 어느 폴더에 넣을까? (새 폴더 `Data_Operation` / 기존 `Data_Analysis` / `Develop`)

둘 다 추천 항목을 골랐다. 그러자 기존 글의 front matter 형식(`layout`, `categories`, `tag`, `toc`)을 그대로 맞춰서 글을 만들고 커밋했다.

### 첫 번째 벽: 푸시 403

커밋까지는 됐는데 푸시가 실패했다.

```
remote: Claude doesn't have GitHub access to mgskko/mgskko.github.io
fatal: unable to access ... The requested URL returned error: 403
```

AI가 저장소를 읽을 수는 있지만, **쓰기 권한은 Claude GitHub App을 저장소에 설치해야** 생긴다. AI는 설치 링크를 알려주고 "처리하면 말해 달라"고 했다. 앱을 설치하고 `다시 푸시해줘` 한 마디로 해결됐다.

> 클라우드 AI 코딩 도구를 처음 쓸 때 가장 먼저 막히는 곳이 권한이다. 읽기와 쓰기는 별개다.

### 두 번째 벽: "너무 짧고 짜치는데"

처음 나온 글은 70줄짜리 개념 정리였다. 솔직히 얇았다.

```
데이터 운영에 대해 너무 글이 짧고 짜치는데 좀더 딥하게 적어봐
지금 너무 얇음 기업에서는 어떻게하는지 이런것들 전부
```

다시 나온 글은 466줄이었다. 파이프라인, 품질 6차원, Airflow DAG 예시, SLA/SLO/SLI, 장애 회고 양식, 거버넌스, 개인정보 처리, 데이터 컨트랙트, 조직 모델(중앙집중형/허브 앤 스포크/데이터 메시)까지 들어갔다.

재밌었던 건 AI가 **"기업 사례는 특정 회사의 실제 내용이 아니라 업계의 일반적인 패턴"이라고 글 안에 스스로 명시**했다는 점이다. 확인 안 된 회사 이야기를 지어내지 않겠다는 거다.

> **배운 것:** 첫 요청이 모호하면 결과도 얕다. "기업에서는 어떻게 하는지 전부"처럼 범위를 말해 줘야 깊이가 나온다.

## 2단계 — CSS만 바꾼 1차 리디자인 (사실상 실패)

이제 본론. 토스 앱 같은 느낌을 원했다. 그래서 디자인 토큰을 정리해서 통째로 붙여 넣었다.

```
전반적으로 ui/ux를 변경해줄수 있어? 지금 너무 별로고 따라한티가 많이 나서
전체적으로 토스 느낌이 나게 바꿔봐

1. 컬러 팔레트
Primary #3182F6 / Background #F2F4F6 / Text Primary #191F28 ...
2. 타이포그래피
Pretendard, 자간 -0.02em, font-variant-numeric: tabular-nums ...
3. 레이아웃
8pt 그리드, 카드 radius 16~24px ...
(이하 생략)
```

AI는 `assets/css/main.scss` 하나를 900줄 넘게 다시 썼다. 색 토큰, Pretendard 폰트, 흰 카드, 알약 모양 태그, 눌렀을 때 살짝 작아지는 효과(`scale(0.98)`)까지.

여기서 인상 깊었던 건 **AI가 직접 빌드하고 스크린샷을 찍어서 확인하는 과정**이었다.

```bash
gem install jekyll ...        # 로컬에 Jekyll 설치
jekyll build -d _site         # 사이트 빌드
node shot.js                  # Playwright로 페이지 열고 스크린샷
```

스크린샷을 보고 스스로 문제를 찾아냈다.

- 목차(TOC) 카드가 본문 카드 위에 40px 겹침
- 페이지네이션 버튼 모서리가 각져 있음 → 테마 쪽 CSS 선택자가 더 구체적이라서 덮어쓰기가 안 됨
- 사이드바에 새 카테고리(`Data_Operation`)가 빠져 있음

다 고치고 병합했다. 그런데 결과를 보니 **여전히 Minimal Mistakes였다.** 색만 바뀐 같은 집이었다.

> **배운 것:** 스킨을 바꿔도 뼈대는 그대로다. HTML 구조가 같으면 "따라한 티"는 안 사라진다.

## 3단계 — 테마를 걷어내고 처음부터

그래서 요청을 다시 했다.

```
css만 바꾸는게 아니라 js랑 html도 바꿔서 먼가 고급져보이게 웹형태로 보고싶다는거였음
포크한거말고 좀 더 웹 자체를 토스느낌의 ui/ux를 사용하고
차트같은거 넣을수 있으면 넣고 동적이게도 하고 전반적으로 싹다 바꾸고 싶음
```

### 결정: Jekyll은 남기고, 테마는 버린다

AI가 먼저 방향을 정리했다. Next.js 같은 걸로 갈아타면 배포 방식(GitHub Actions 설정)까지 바뀌어야 한다. 그래서 **GitHub Pages가 지금처럼 자동 빌드하는 Jekyll은 유지하고, 테마 파일만 전부 지우고 직접 만든다**로 갔다. 외부 라이브러리도 쓰지 않기로 했다.

지운 것과 새로 만든 것은 이렇다.

| 구분 | 내용 |
|---|---|
| 삭제 | 테마 레이아웃·Sass·JS, 테마 문서 `docs/`, 테스트 `test/`, 테마용 GitHub 워크플로 |
| 유지 | 글 197개, 이미지, 파비콘, 글 주소와 카테고리 주소 |
| 새로 작성 | 레이아웃 5개, include 10여 개, `main.css`, `app.js`, `charts.js`, `search.json` |

테마용 워크플로 중에는 **PR 본문이 비어 있으면 자동으로 닫아버리는 것**도 있었다. 원래 테마 저장소로 잘못 들어오는 PR을 막으려는 용도인데, 내 블로그엔 필요 없는 거였다. 이것도 같이 지웠다.

### 디자인 토큰부터

모든 색과 간격을 CSS 변수로 먼저 정의했다. 다크 모드는 같은 이름의 변수 값만 바꾼다.

```css
:root {
  --bg: #f2f4f6;        /* 페이지 바탕 */
  --surface: #ffffff;   /* 카드 */
  --t1: #191f28;        /* 제목 */
  --t2: #4e5968;        /* 본문 */
  --t3: #8b95a1;        /* 보조 */
  --blue: #3182f6;
  --r-lg: 20px;         /* 카드 둥글기 */
}
:root[data-theme="dark"] {
  --bg: #101114;
  --surface: #1b1d22;
  --t1: #f2f4f6;
  /* ... */
}
```

GitHub Pages는 오래된 Sass 컴파일러를 쓴다. 최신 CSS 함수(`clamp()` 등)를 Sass 안에 쓰면 빌드가 깨질 수 있어서, **아예 순수 CSS로 작성**했다. 이런 판단을 AI가 먼저 해 줬다.

### 만든 것들

**홈 = 대시보드**

- 숫자가 0부터 올라가는 요약 카드 (전체 글, 다룬 분야, 가장 오래 이어 쓴 기록, 최근 글)
- 작성한 날 **히트맵** (GitHub 잔디 같은 것)
- **월별 막대 차트**, **많이 쓴 분야 순위**
- 연도 버튼(2026 / 2023 / 2022)을 누르면 세 차트가 그 해 기록으로 바뀜

차트 라이브러리 없이 SVG를 직접 그렸다. 막대 위쪽만 둥글게 만드는 경로도 손으로 계산한다.

```js
function roundTop(x, y, w, h, r) {
  r = Math.min(r, h, w / 2);
  return "M" + x + "," + (y + h) + "V" + (y + r) +
    "Q" + x + "," + y + " " + (x + r) + "," + y +
    "H" + (x + w - r) + "Q" + (x + w) + "," + y + " " + (x + w) + "," + (y + r) +
    "V" + (y + h) + "Z";
}
```

분야 색은 눈대중으로 고르지 않았다. AI가 **색각 이상(색맹) 시뮬레이션까지 하는 팔레트 검증 스크립트**를 돌려서 통과한 색만 썼다. 밝은 모드에서 일부 색의 대비가 낮다는 경고가 나오자, 범례에 이름과 글 수를 항상 같이 표시하는 것으로 보완했다.

**검색 = 커맨드 팔레트**

`⌘K`(윈도우는 `Ctrl+K`)나 `/`를 누르면 검색창이 뜬다. 빌드할 때 `search.json`에 전체 글 제목·태그·본문을 담아 두고, 검색창을 처음 열 때만 불러온다. 첫 화면 속도에는 영향이 없다.

**글 상세**

- 상단 읽기 진행 막대
- 오른쪽에 따라오는 목차 + 지금 읽는 위치 표시 (모바일은 아래에서 올라오는 바텀시트)
- 코드 블록 복사 버튼, 이미지 확대, "링크를 복사했어요" 토스트
- 화면에 보일 때만 불러오는 댓글

### 여기서 터진 버그들

순조롭지 않았다. 스크린샷으로 확인할 때마다 뭔가 하나씩 깨져 있었다.

#### ❌ 1. include에 대괄호를 넣으면 빌드가 죽는다

{% raw %}
```liquid
{% include cat-meta.html key=p.categories[0] %}
```
{% endraw %}

```
Liquid Exception: Invalid syntax for include tag: key=p.categories[0]
```

include 파라미터에는 대괄호를 못 쓴다. 변수에 먼저 담아서 넘기는 걸로 해결했다.

{% raw %}
```liquid
{% assign pk = p.categories[0] %}
{% include cat-meta.html key=pk %}
```
{% endraw %}

#### ❌ 2. 카테고리 페이지 글 수가 전부 0

빌드는 되는데 카테고리 페이지의 모든 숫자가 0으로 나왔다. AI가 디버그용 페이지를 따로 만들어서 하나씩 찍어 봤다.

```
A=56 B=56 C=18      ← site.categories["Programmers"] 는 정상
E=56                ← 키를 변수에 담으면 정상
[Programmers:0:]    ← site.categories[item[0]] 은 0
```

원인은 Liquid가 **`site.categories[item[0]]`처럼 대괄호 안에 또 대괄호가 있는 조회를 처리하지 못한다**는 것이었다. 오류도 안 내고 조용히 빈 값을 돌려준다. 같은 문제가 검색 데이터에도 있어서, 검색 결과에 "데이터 운영" 대신 `Data_Operation`이 그대로 찍히고 있었다. 둘 다 1번과 같은 방법으로 고쳤다.

#### ❌ 3. 글 본문이 통째로 안 보인다

화면에 들어올 때 살짝 떠오르는 애니메이션을 넣었는데, 글 상세에서 **본문 카드가 아예 안 나타났다.** 등장 판정 기준이 "요소의 8%가 화면에 보이면"이었는데, 글 본문은 수천 픽셀짜리라 8%가 화면보다 컸다. 영원히 조건을 못 채운 것이다. 기준을 "조금이라도 보이면"으로 바꿔서 해결했다.

#### ❌ 4. 분명히 있는 단어가 검색이 안 된다

"파이프라인"을 검색했는데 결과가 0개였다. 데이터 운영 글에 수십 번 나오는 단어인데. 검색 데이터에 본문을 **앞 1,200자만** 넣고 있어서였다. 공백을 정리하고 3,000자까지 늘렸다.

#### ❌ 5. 수식이 예전부터 깨져 있었다

선형대수 글의 행렬 수식을 확인하다가 알게 됐다. 이전 테마는 **이미 서비스가 종료된 `cdn.mathjax.org` 주소**로 MathJax를 불러오고 있었다. 즉 리뉴얼 전부터 수식이 안 보였을 가능성이 크다. MathJax 3로 바꿨다.

그런데 AI가 일하는 클라우드 환경에서는 외부 CDN(`cdn.jsdelivr.net`)이 막혀 있었다. 그래서 AI는 **npm에서 같은 버전을 받아서, 브라우저 테스트 중에 그 요청만 로컬 파일로 연결**해 수식이 실제로 그려지는 것까지 확인했다. 그냥 "될 거예요"라고 넘어가지 않은 게 좋았다.

## 4단계 — 글 내용을 보고 화면을 바꾸기

여기까지 와도 뭔가 아쉬웠다. 화면은 예뻐졌는데 **글 자체가 읽기 편해진 건 아니었다.** 그래서 이렇게 요청했다.

```
https://collectui.com/
여기 사이트 참고해서 ui 인터렉트나 디자인이나 이런거 엄청 다양한데
한번 참고하면서 동적으로 누가봐도 가독성 좋게 못하냐?
너는 ui/ux 30년차 디자이너여서 쉽게 개발할수 있음
글 내용을 보고 어떤방식으로 할수 있는지 한번 해봐
```

참고 사이트는 AI 쪽 네트워크 정책 때문에 열리지 않았다. AI는 그 사실을 숨기지 않고 말한 다음, 대신 **내 글 197개를 전부 분석**했다.

### 글 197개를 분석한 결과

제목 패턴을 뽑아 보니 이랬다.

```
[백준 1931번] [🥈1] 회의실 배정 (python)
[프로그래머스] ⭐⭐⭐⭐ 그룹별 조건에 맞는 식당 목록 출력하기 (MySQL)
[OS] 운영체제(1장) 운영체제 소개 - 2
[혼공머신러닝] 3 - 1 k - 최근접 이웃 회귀
4편. 자체전이라는 괴물 — 가장 복잡한 로직과의 싸움
```

코딩테스트 글의 소제목 빈도도 셌다.

| 소제목 | 등장 횟수 |
|---|---|
| `### 코드` | 95 |
| `### 문제` | 93 |
| `### 예제 입력` / `### 예제 출력` | 각 82 |
| `### 입력` / `### 출력` | 각 42 |
| `### 문제를 풀면서 막혔던 부분` | 32 |
| `### 풀이` | 29 |

태블로 글에는 스크린샷이 **234장**이나 있었다. 이 숫자들을 보고 나니 무엇을 해야 할지가 보였다.

| 글 유형 | 문제 | 바꾼 방식 |
|---|---|---|
| 코딩테스트 (98개) | 제목에 이모지·별·괄호가 섞여 읽기 힘듦, 문제부터 코드까지 한 줄로 길게 이어짐 | 제목 → 난이도 배지 + 깔끔한 제목, 문제 영역 탭, 예제 입출력 나란히, 코드 버전 탭 |
| 시리즈 | 몇 편 중 몇 번째인지 모름 | 시리즈 진행 막대, 전체 회차 목록, 다음 편 버튼 |
| 태블로 실습 | 문단·스크린샷이 끝없이 반복 | 번호 붙은 단계 카드, 넘겨 보는 갤러리 |
| 개념 정리 | `**용어** : 설명` 목록, 보라·빨강 원색 글씨 | 용어 카드, 테마 색으로 통일 |

### 핵심 원칙: 마크다운 원본은 건드리지 않는다

197개 글을 하나하나 고치는 대신, **빌드할 때와 브라우저에서 글 구조를 읽어서 화면만 바꾸는** 방식을 택했다. 원본은 그대로니까 언제든 되돌릴 수 있다.

#### 제목 분해 — 별 개수 세기 트릭

프로그래머스 난이도는 제목의 ⭐ 개수다. Liquid에는 "글자 세기" 함수가 없어서, **⭐로 문자열을 쪼갠 뒤 조각 수에서 1을 빼는** 방법을 썼다.

{% raw %}
```liquid
{% assign tp_stars = t | split: "⭐" | size | minus: 1 %}
{% assign tp_level = tp_stars | prepend: "Lv." %}
```
{% endraw %}

백준은 🥉🥈🥇 이모지로 티어를 판별하고, 괄호 안 언어를 뽑고, 남은 부분을 제목으로 쓴다. 그 결과 이렇게 바뀐다.

```
[백준 1931번] [🥈1] 회의실 배정 (python)
→ [Silver 1] [#1931] [Python]  회의실 배정
```

AI는 이 규칙을 만든 뒤 **197개 글 전체를 한 번에 분해해서 결과 표를 출력**하고, 하나도 안 틀렸는지 확인했다.

#### 코딩테스트 글 재구성

브라우저에서 `###` 소제목을 기준으로 글을 섹션으로 나누고, 이름에 따라 다르게 조립한다.

- `문제`, `입력`, `출력`, `예제 입력 N`, `예제 출력 N` → **탭 하나짜리 문제 카드**로 묶음. 예제는 입력·출력을 나란히
- `풀이` → 파란 카드
- `막혔던 부분`, `틀렸던 과정` → 빨간 카드. 그 안의 `❌ 시도 1`, `❌ 시도 2`는 **타임라인**으로
- `코드` 아래 `ver(1)`, `ver(2)`가 있으면 → **"풀이 1 / 풀이 2" 탭**
- 26줄이 넘는 코드는 접어 두고 "코드 전체 보기"

본문 맨 위의 "백준 사이트 링크" 박스는 제목 옆 **"문제 보러 가기" 버튼**으로 옮겼다.

#### 카테고리 페이지에 난이도 분포

백준·프로그래머스 카테고리 페이지에는 난이도 분포 차트를 넣었다. 막대를 누르면 그 난이도 글만 걸러진다. 만들고 보니 내가 **Silver 5를 16문제로 가장 많이 풀었고, 프로그래머스는 Lv.2가 25문제로 제일 많았다.** 내 공부 패턴이 숫자로 보이니 묘하게 반성하게 된다.

### 작은 해프닝: 안전장치에 막히다

중간에 AI가 긴 스크립트를 한 번에 실행하려다가 Claude Code의 **안전 검사에 막혔다.** 명령이 길고 복잡해서 검사기가 정확히 해석하지 못했고, "뭔가를 지우는 명령일 가능성을 배제할 수 없다"며 실행을 멈춘 것이다. 실제로는 아무것도 지우지 않는 명령이었다.

AI는 검사를 우회하지 않고, 같은 내용을 **스크립트 파일로 따로 저장한 다음 실행**하는 정석적인 방법으로 처리했다. 그리고 나한테 "삭제 작업은 들어 있지 않다"고 설명했다. 이런 안전장치가 있다는 것 자체가 AI에게 저장소를 맡길 때 안심이 되는 부분이다.

## 5단계 — "모니터가 큰데 글은 너무 좁다"

병합하고 내 모니터로 열어 봤더니 문제가 바로 보였다.

```
근데 지금 문제가 모바일말고 모니터인경우 양옆에 여백이 너무 많아
그래서 글이 너무 좁게 보여 화면에 맞게 세팅값을 바꿔야됨
```

원인은 단순했다. 전체 폭 1080px, 글 본문 760px로 **고정**되어 있었다. 2560px 모니터에서는 양옆이 각각 900px씩 비어 있었던 거다.

AI는 폭을 변수로 빼고, 화면이 커질수록 단계적으로 늘렸다. 핵심은 이 한 줄이다.

```css
@media (min-width: 1200px) {
  /* 본문 폭 = 전체 폭 - 목차 - 간격 - 양쪽 여백 */
  :root { --read: calc(var(--wrap) - var(--toc) - var(--toc-gap) - var(--gutter) * 2); }
}
```

본문 폭을 고정값이 아니라 **계산값**으로 만들었기 때문에, 상단 바·본문·목차의 가장자리가 항상 같은 선에 맞는다.

| 화면 폭 | 글 본문 폭 (전 → 후) | 한쪽 여백 (전 → 후) |
|---|---|---|
| 1366px | 760px → 780px | 약 300px → 163px |
| 1920px | 760px → 1,172px | 약 580px → 220px |
| 2560px | 760px → 1,428px | 약 900px → 388px |

### 그런데 "여전히 좁은데?"

배포하고 바로 열어 봤는데 여전히 좁았다. 스크린샷을 찍어서 보냈다.

```
이거 보셈 글 목록 들어가면 여백 엄청 많고 글은 짧다니까?
```

AI의 답은 의외였다. **"보내주신 화면은 새 버전이 아니라 이전 버전이에요."** 근거도 댔다. 새 버전이라면 제목의 `[데이터 운영] 1.`이 "1편" 배지로 바뀌어 있어야 하는데, 스크린샷에는 원래 제목이 그대로 있다는 것이다.

GitHub Pages는 HTML을 최대 10분 정도 캐시한다. `Ctrl + F5`로 강력 새로고침하니 넓어진 화면이 떴다.

> **배운 것:** "안 바뀌었다"고 느낄 때 스크린샷을 보내면, 무엇이 안 바뀌었는지가 정확히 드러난다. 말로 "안 돼"보다 훨씬 빠르다.

## 번외의 번외 — 이 글을 쓰다가 발견한 버그

이 글을 써 달라고 했더니, AI가 글을 쓰기 전에 기존 바이브코딩 글의 형식부터 읽었다. 그러다 4편에 들어 있는 다이어그램(`<div class="mermaid">`)을 발견했다.

확인해 보니 **이전 테마는 Mermaid 다이어그램 라이브러리를 불러오고 있었는데, 새 테마로 갈아엎으면서 그게 빠져 있었다.** 다이어그램을 쓰는 글 5개에서 그림 대신 코드 텍스트가 그대로 보이고 있었던 거다. 나도 몰랐다.

AI는 다이어그램이 있는 글에서만 Mermaid를 불러오도록 고쳤다. 버전을 고정하고, 다크 모드일 때는 다이어그램도 어두운 테마로 그리게 했다. 이 글에 들어간 다이어그램 두 개도 그 덕분에 보이는 것이다.

> **배운 것:** 갈아엎을 때는 기존 기능 목록부터 만들어야 한다. "원래 되던 것"은 원래 되던 거라 아무도 확인하지 않는다.

## 바이브코딩으로 블로그를 만들며 배운 것

- **요청은 수치로.** "토스 느낌"보다 `#3182F6`, `radius 16px`, `8pt 그리드`를 붙여 넣었을 때 결과가 훨씬 정확했다.
- **"싫다"도 구체적으로.** "따라한 티가 난다", "모니터가 큰데 글이 좁다"처럼 무엇이 문제인지 말하면 AI가 원인을 찾아간다.
- **검증을 AI에게 시킨다.** 빌드하고, 스크린샷을 찍고, 빌드 로그를 확인하는 것까지 요청하지 않아도 했다. 대신 "확인하지 못한 것"도 따로 알려줬다. 이 부분을 꼭 읽어야 한다.
- **원본은 보존한다.** 글 197개는 한 글자도 안 바꿨다. 화면만 바꿨으니 언제든 되돌릴 수 있다.
- **환경 제약은 숨기지 않는다.** 권한이 없을 때, 사이트가 안 열릴 때, CDN이 막혔을 때 AI는 그 사실을 먼저 말하고 다른 방법을 찾았다.

풋살 앱을 만들 때는 내가 Gemini에게 프롬프트를 쓰고, 결과를 Lovable에 붙여 넣고, Supabase에서 직접 SQL을 돌렸다. 이번에는 그 모든 손작업을 AI가 했고, 나는 **"무엇을 원하는지"와 "무엇이 마음에 안 드는지"만** 말했다. 바이브코딩의 다음 단계는 결국 이거라고 생각한다.

> **코드를 쓰는 사람에서, 기준을 말하는 사람으로.**

## 데이터 운영(Data Operations)이란?

> 데이터가 **정해진 시간에, 정확한 값으로, 필요한 사람에게, 안전하게** 도착하도록 만드는 모든 활동

분석이나 모델링은 "데이터가 믿을 만하다"는 전제 위에서만 의미가 있다.
데이터 운영은 그 전제를 **한 번이 아니라 매일 지속적으로** 만들어 내는 일이다.

---

## 1. 왜 필요한가

현업에서 데이터 때문에 생기는 문제는 대부분 분석 기술이 아니라 **운영** 문제다.

| 증상 | 실제 원인 |
|---|---|
| 대시보드 숫자가 어제와 다르다 | 배치가 늦게 끝났거나 중간에 실패했다 |
| 팀마다 매출 숫자가 다르다 | 지표 정의가 문서화되지 않았다 |
| 갑자기 매출이 0으로 찍힌다 | 원천 시스템의 스키마가 바뀌었다 |
| 모델 성능이 서서히 떨어진다 | 입력 데이터의 분포가 바뀌었다 (drift) |
| 이 테이블 써도 되는지 모르겠다 | 오너와 설명이 없다 |
| 개인정보가 분석 환경에 그대로 있다 | 접근 통제와 마스킹이 없다 |

핵심은 **"문제가 생겼다"가 아니라 "문제가 생긴 걸 누가, 얼마나 빨리 아느냐"** 이다.
운영이 없으면 이런 문제를 **쓰는 사람이 먼저 발견**한다.
운영이 있으면 **만드는 쪽이 먼저 발견하고 고친다.**

---

## 2. 데이터 흐름 전체 그림

```
[원천]            [수집]          [저장]           [변환]            [제공]
 서비스 DB   ─┐
 로그/이벤트 ─┼─▶ 배치 / 스트리밍 ─▶ Data Lake ─▶ 정제·집계(ELT) ─▶ Data Mart ─▶ BI·분석
 외부 API    ─┤     CDC                (Raw)        (Staging→Mart)      │          ML 학습
 파일/수기   ─┘                                                          └─▶ API / 리포트

 ───────────────────────────────────────────────────────────────────────────────
 [운영 영역] 오케스트레이션 · 품질 검증 · 모니터링/알림 · 메타데이터/카탈로그
             권한/보안 · 비용 관리 · 장애 대응 · 문서화
```

운영은 위 흐름의 **어느 한 단계가 아니라 모든 단계를 가로지르는 층**이다.

## 3. 운영 영역별 상세

### 3-1. 수집·적재

| 방식 | 설명 | 특징 |
|---|---|---|
| 배치(Batch) | 일/시간 단위로 묶어서 가져온다 | 구현이 단순하고 재처리가 쉽다. 지연이 있다 |
| 스트리밍 | 이벤트가 발생하는 즉시 처리한다 (Kafka 등) | 실시간이지만 운영 난이도가 높다 |
| CDC(Change Data Capture) | DB의 변경분만 읽어서 반영한다 | 원천 DB 부하가 적고 삭제/수정 추적이 가능하다 |
| 파일/수기 | 엑셀, CSV 업로드 | 형식이 제각각이라 **검증이 특히 중요하다** |

운영에서 꼭 챙기는 것:

 - **멱등성(Idempotency)** : 같은 작업을 두 번 돌려도 결과가 같아야 한다. (중복 적재 방지)
 - **재처리(Backfill)** : 과거 특정 기간을 다시 돌릴 수 있어야 한다.
 - **증분 적재 기준** : 어떤 컬럼(수정일 등)을 기준으로 어디까지 가져왔는지 기록한다.
 - **원본 보존(Raw 레이어)** : 가공 전 원본은 건드리지 않고 남겨 둔다. 문제가 생기면 여기서 다시 만든다.

### 3-2. 변환 (ETL vs ELT)

 - **ETL** : 변환(T)을 하고 나서 적재(L)한다. 전통적인 방식이다.
 - **ELT** : 먼저 적재하고 DW 안에서 SQL로 변환한다. 클라우드 DW(BigQuery, Snowflake 등)에서 일반적이다.

최근에는 변환을 **SQL + 버전관리 + 테스트**로 관리하는 방식(dbt 등)이 많이 쓰인다.
레이어를 나누는 것이 기본이다.

```
raw (원본)  →  staging (타입·이름 정리)  →  intermediate (조인·가공)  →  mart (지표·분석용)
```

레이어를 나누면 **어디서 값이 틀어졌는지 역추적**하기 쉽다.

### 3-3. 오케스트레이션

작업 간 **순서와 의존성, 스케줄, 재시도, 실패 알림**을 관리한다. (Airflow, Dagster, Prefect 등)

```python
# Airflow DAG 예시 (개념 파악용)
from airflow import DAG
from airflow.operators.python import PythonOperator
from datetime import datetime, timedelta

default_args = {
    "retries": 2,                          # 실패 시 재시도
    "retry_delay": timedelta(minutes=5),
    "email_on_failure": True,              # 실패 알림
}

with DAG("daily_sales", start_date=datetime(2026, 1, 1),
         schedule="0 3 * * *", catchup=False, default_args=default_args) as dag:

    extract = PythonOperator(task_id="extract", python_callable=extract_fn)
    validate = PythonOperator(task_id="validate", python_callable=validate_fn)
    load = PythonOperator(task_id="load", python_callable=load_fn)

    extract >> validate >> load            # 검증을 통과해야만 적재
```

포인트는 **"검증 단계를 파이프라인 안에 넣는다"** 는 것이다. 사후에 확인하는 게 아니라 틀린 데이터가 아래로 흘러가지 못하게 막는다.

### 3-4. 저장 구조

| 구조 | 설명 |
|---|---|
| Data Warehouse | 정형 데이터를 분석용으로 정리해 둔 저장소 |
| Data Lake | 정형/비정형 원본을 그대로 쌓아 두는 저장소 |
| Lakehouse | 레이크의 유연성과 웨어하우스의 관리 기능을 합친 구조 |
| Data Mart | 부서·목적별로 잘라 만든 분석용 테이블 묶음 |

## 4. 데이터 품질 관리

### 4-1. 품질 차원

| 차원 | 질문 | 검증 예시 |
|---|---|---|
| 정확성 | 실제 값과 맞는가 | 원천 시스템과 합계 대조 |
| 완전성 | 빠진 값이 없는가 | 필수 컬럼 null 비율 |
| 유일성 | 중복이 없는가 | PK 중복 검사 |
| 일관성 | 시스템 간 같은 값인가 | 코드값·단위 통일 여부 |
| 유효성 | 형식과 범위가 맞는가 | 날짜 형식, 값의 허용 범위 |
| 적시성 | 제때 최신인가 | 마지막 갱신 시각 |

### 4-2. 검증 수준

품질 검사는 깊이에 따라 나눠서 설계한다.

 1. **스키마 검증** : 컬럼 존재 여부, 타입, nullable
 2. **통계 검증** : 건수, 평균, 분포가 평소 범위인가 (전일 대비 ±30% 등)
 3. **비즈니스 룰 검증** : "결제금액 ≥ 0", "종료일 ≥ 시작일", "주문 수 = 결제 수 + 취소 수"
 4. **정합성 검증** : 원천 건수 = 적재 건수, 마트 합계 = 원본 합계

### 4-3. 코드 예시

```python
import pandas as pd

def check_quality(df: pd.DataFrame) -> list[str]:
    errors = []

    # 1) 스키마
    required = {"order_id", "user_id", "amount", "created_at"}
    missing = required - set(df.columns)
    if missing:
        errors.append(f"누락 컬럼: {missing}")
        return errors

    # 2) 완전성 / 유일성
    if df["order_id"].isnull().any():
        errors.append("order_id에 null 존재")
    if df["order_id"].duplicated().any():
        errors.append(f"order_id 중복 {df['order_id'].duplicated().sum()}건")

    # 3) 유효성 (비즈니스 룰)
    if (df["amount"] < 0).any():
        errors.append("amount 음수 존재")

    # 4) 적시성
    latest = pd.to_datetime(df["created_at"]).max()
    if latest < pd.Timestamp.now() - pd.Timedelta(hours=26):
        errors.append(f"최신 데이터가 오래됨: {latest}")

    return errors

errors = check_quality(df)
if errors:
    raise ValueError("\n".join(errors))   # 파이프라인 중단 + 알림
```

SQL로 정합성을 보는 예시이다.

```sql
-- 원천 건수와 적재 건수 대조
SELECT
  s.cnt AS source_cnt,
  t.cnt AS target_cnt,
  s.cnt - t.cnt AS diff
FROM (SELECT COUNT(*) cnt FROM src.orders WHERE dt = '2026-11-24') s,
     (SELECT COUNT(*) cnt FROM dw.orders  WHERE dt = '2026-11-24') t;
```

### 4-4. 실패했을 때 어떻게 할까

 - **차단(Block)** : 파이프라인을 멈추고 다음 단계로 넘기지 않는다. (핵심 지표)
 - **경고(Warn)** : 통과시키되 알림을 보낸다. (참고용 지표)
 - **격리(Quarantine)** : 문제 행만 따로 빼서 보관하고 나머지는 진행한다.

모든 검사를 차단으로 두면 사소한 일에도 서비스가 멈춘다.
**중요도에 따라 차단/경고를 나누는 것**이 운영 설계의 핵심이다.

## 5. 모니터링과 데이터 옵저버빌리티

서버 모니터링이 CPU·메모리를 본다면, 데이터 모니터링은 **데이터 자체의 건강**을 본다.

| 5대 관측 항목 | 확인 내용 |
|---|---|
| Freshness (신선도) | 마지막 갱신이 언제인가 |
| Volume (양) | 건수가 평소와 비슷한가 |
| Schema (구조) | 컬럼이 추가·삭제·변경되었는가 |
| Distribution (분포) | 값의 분포·null 비율이 달라졌는가 |
| Lineage (계보) | 이 데이터는 어디서 와서 어디로 가는가 |

**Lineage**는 장애 때 특히 중요하다.
"이 원천 테이블이 깨졌다 → 영향받는 마트 7개, 대시보드 12개"를 즉시 알 수 있어야 대응 범위가 정해진다.

### SLA / SLO / SLI

서비스 운영의 개념을 데이터에도 그대로 가져온다.

| 용어 | 의미 | 데이터 예시 |
|---|---|---|
| SLI | 측정 지표 | 일 매출 테이블 갱신 완료 시각 |
| SLO | 내부 목표 | 매일 오전 8시까지 99% 완료 |
| SLA | 사용자와의 약속 | 오전 9시까지 지연되면 사전 공지 |

"데이터 잘 줄게요"가 아니라 **"몇 시까지, 몇 % 보장"** 처럼 숫자로 약속해야 운영이 가능하다.

## 6. 장애 대응 프로세스

데이터 장애도 서비스 장애처럼 다룬다.

```
감지 → 분류(심각도) → 영향 범위 파악 → 임시 조치 → 원인 수정 → 재처리 → 공유 → 회고
```

### 심각도 예시

| 등급 | 기준 | 대응 |
|---|---|---|
| P1 | 핵심 지표·정산·대외 리포트 오류 | 즉시 대응, 관련 부서에 즉시 공유 |
| P2 | 주요 대시보드 지연·오류 | 당일 해결 |
| P3 | 참고용 테이블 문제 | 일정 내 해결 |

### 장애 대응 시 체크 항목

 1. 어디서 틀어졌나? (lineage로 역추적)
 2. 영향받는 하위 테이블과 사용자는 누구인가?
 3. 잘못된 데이터를 이미 가져다 쓴 곳이 있는가? → **정정 공지**
 4. 수정 후 **백필**로 과거 기간을 다시 채웠는가?
 5. 같은 문제가 재발하지 않도록 **검증 룰을 추가**했는가?

### 회고(Post-mortem)

비난이 아니라 **구조 개선**이 목적이다.
"누가 실수했나"가 아니라 "왜 실수가 시스템을 통과할 수 있었나"를 적는다.

```
- 무슨 일이 있었나 (타임라인)
- 영향 범위
- 근본 원인
- 왜 사전에 못 잡았나
- 재발 방지 조치 (담당자 / 기한)
```

## 7. 데이터 거버넌스

> 누가, 어떤 데이터를, 어떤 규칙으로, 어떻게 쓰는지 정하는 체계

### 7-1. 역할

| 역할 | 하는 일 |
|---|---|
| 데이터 오너 | 해당 데이터의 **의사결정 책임자**. 정의, 공개 범위, 품질 기준을 결정한다 |
| 데이터 스튜어드 | **실무 관리자**. 정의 문서화, 품질 이슈 처리, 변경 관리를 한다 |
| 데이터 엔지니어 | 파이프라인과 플랫폼을 만들고 운영한다 |
| 데이터 분석가 | 데이터를 사용해 인사이트를 만들고, 품질 이슈를 가장 먼저 발견한다 |
| 보안/개인정보 담당 | 접근 통제, 마스킹, 법규 준수를 점검한다 |

"오너가 없는 테이블"이 가장 위험하다. 문제가 생겨도 아무도 책임지지 않기 때문이다.

### 7-2. 메타데이터와 데이터 카탈로그

 - **비즈니스 메타데이터** : 컬럼 설명, 지표 정의, 담당자
 - **기술 메타데이터** : 스키마, 타입, 파티션, 갱신 주기
 - **운영 메타데이터** : 마지막 갱신 시각, 실행 이력, 사용량

이를 한곳에서 검색하게 해 주는 것이 **데이터 카탈로그**다. (DataHub, Amundsen, 클라우드 사업자 카탈로그 등)

**지표 정의 예시** (문서화가 안 되면 팀마다 숫자가 달라진다)

```
지표명  : 순매출
정의    : 결제금액 - 환불금액 - 쿠폰할인금액
기준일  : 결제 완료 시각 (KST)
제외    : 테스트 계정, 내부 직원 주문
오너    : 커머스 분석팀
갱신    : 매일 07:00
```

### 7-3. 접근 권한과 보안

 - **최소 권한 원칙** : 업무에 필요한 만큼만 연다
 - **역할 기반 접근 제어(RBAC)** : 개인이 아니라 역할에 권한을 부여한다
 - **컬럼 단위 통제** : 같은 테이블에서도 민감 컬럼만 가린다
 - **접근 로그 감사** : 누가 언제 무엇을 조회했는지 기록한다

### 7-4. 개인정보 처리

개인정보가 들어 있는 데이터는 분석 편의보다 **법적 의무**가 우선이다. (국내는 개인정보 보호법 적용)

| 기법 | 설명 | 예시 |
|---|---|---|
| 마스킹 | 일부를 가린다 | 010-****-1234 |
| 가명처리 | 식별자를 다른 값으로 바꾼다 (복원 키는 분리 보관) | user_id → 해시값 |
| 익명처리 | 어떤 방법으로도 특정할 수 없게 한다 | 집계 통계만 제공 |
| 암호화 | 저장·전송 시 암호화한다 | 컬럼 단위 암호화 |

 - 수집 목적에 필요한 최소한만 수집한다
 - **보존 기간**을 정하고 지나면 파기한다
 - 분석 환경에는 원칙적으로 **가명 처리된 데이터**만 둔다

### 7-5. 데이터 컨트랙트

데이터를 **만드는 쪽과 쓰는 쪽이 맺는 약속**이다.

```yaml
# 예시: orders 테이블 컨트랙트
dataset: orders
owner: commerce-platform
schema:
  - {name: order_id, type: string,  nullable: false, unique: true}
  - {name: amount,   type: integer, nullable: false, min: 0}
sla:
  freshness: "매일 07:00까지"
change_policy: "컬럼 삭제/타입 변경은 2주 전 공지"
```

원천 시스템 개발팀이 컬럼을 마음대로 바꿔서 하위 파이프라인이 깨지는 문제를 **사전 합의**로 줄이는 방법이다.

## 8. 조직은 어떻게 구성하는가

| 모델 | 구조 | 장점 | 단점 |
|---|---|---|---|
| 중앙집중형 | 한 데이터팀이 수집·가공·분석을 모두 담당 | 표준화가 쉽고 품질 일관성이 높다 | 요청이 몰려 병목이 생긴다 |
| 분산형 | 각 부서가 자체 데이터 인력을 둔다 | 현업 이해도가 높고 속도가 빠르다 | 지표 정의가 팀마다 달라진다 |
| 허브 앤 스포크 | 중앙은 플랫폼·표준, 부서는 분석·도메인 데이터 | 균형이 좋다. 많은 기업이 수렴하는 형태 | 역할 경계를 명확히 해야 한다 |
| 데이터 메시 | 도메인별로 데이터를 "제품"처럼 책임지고, 플랫폼은 공통 인프라 제공 | 대규모 조직에 확장성이 좋다 | 도입 난이도와 조직 성숙도 요구가 높다 |

### 규모별로 보통 이런 모습이다 (일반적인 경향)

| 규모 | 일반적인 형태 |
|---|---|
| 초기 스타트업 | 한두 명이 수집·분석·대시보드까지 모두 한다. 자동화와 문서화가 가장 먼저 무너진다 |
| 성장기 기업 | 데이터 엔지니어링팀 신설. 파이프라인 표준화, 오케스트레이션·DW 도입, 지표 정의 정리 시작 |
| 대기업 | 데이터 플랫폼팀 + 거버넌스 조직 + 도메인별 분석 조직. 카탈로그·권한·표준 용어 체계를 공식 프로세스로 운영 |

> 위 내용은 업계에서 널리 알려진 일반적인 패턴을 정리한 것이다. 개별 회사의 실제 조직과 도구는 다를 수 있다.

### 대기업에서 흔한 운영 장치

 - **표준 용어/지표 사전** : 전사에서 같은 말은 같은 정의로 쓴다
 - **데이터 관리 위원회** : 정책·우선순위·분쟁을 조정한다
 - **변경 관리 프로세스** : 스키마 변경 시 영향도 분석과 사전 공지를 거친다
 - **데이터 품질 지표 관리** : 품질 점수를 정기적으로 측정해 조직 성과와 연결한다
 - **온콜(On-call) 체계** : 파이프라인 장애를 담당 순번이 즉시 대응한다
 - **비용 관리(FinOps)** : 쿼리·저장 비용을 팀별로 추적하고 최적화한다

## 9. AI/ML 데이터 운영 (라벨링 데이터 포함)

모델을 만들 때는 데이터 운영의 대상이 **테이블에서 데이터셋**으로 넓어진다.

| 항목 | 운영 포인트 |
|---|---|
| 라벨링 가이드라인 | 애매한 케이스 기준을 문서로 고정하고 버전 관리한다 |
| 검수 체계 | 작업 → 1차 검수 → 샘플링 재검수의 단계를 둔다 |
| 품질 지표 | 검수 통과율, 작업자 간 일치도(IAA), 오류 유형별 비율 |
| 데이터 버전 관리 | "이 모델은 어떤 버전의 데이터로 학습했는가"를 추적한다 (DVC 등) |
| 분포 변화 감시 | 서비스 환경이 바뀌어 입력 분포가 달라졌는지 본다 (drift) |
| 학습/검증 분리 | 같은 원본이 학습과 검증에 섞이는 누수를 막는다 |

**작업 현황 관리도 운영의 일부**다.
일별 작업량, 진행률, 반려율, 작업자별 편차를 지표로 관리해야 일정과 품질을 함께 잡을 수 있다.

## 10. 데이터 운영 성숙도

| 단계 | 모습 |
|---|---|
| 1. 사람 의존 | 담당자가 수동으로 돌린다. 문제는 사용자 문의로 알게 된다 |
| 2. 자동화 | 스케줄러로 자동 실행한다. 실패 알림이 있다 |
| 3. 검증 내장 | 파이프라인에 품질 검증이 들어 있고 차단/경고 기준이 있다 |
| 4. 관측·계약 | 옵저버빌리티, SLA, 데이터 컨트랙트, 카탈로그를 운영한다 |
| 5. 최적화 | 품질·비용·사용성을 지표로 지속 개선한다 |

한 번에 5단계를 노릴 필요는 없다. **현재 단계에서 가장 아픈 문제 하나**부터 푸는 것이 현실적이다.

### 도입 로드맵 (현실적인 순서)

 1. **핵심 지표 3~5개**를 정하고 정의를 문서화한다
 2. 그 지표를 만드는 파이프라인에 **실패 알림**을 건다
 3. 건수·null·중복 같은 **기본 검증**을 추가한다
 4. **오너와 갱신 시각**을 테이블에 명시한다
 5. 장애가 나면 **회고를 남기고 검증 룰로 환원**한다
 6. 여유가 생기면 카탈로그, lineage, 컨트랙트로 확장한다

## 11. 운영 체크리스트

**파이프라인**
 - [ ] 재실행해도 결과가 같은가 (멱등성)
 - [ ] 과거 기간을 다시 채울 수 있는가 (백필)
 - [ ] 실패 시 재시도와 알림이 있는가
 - [ ] 원본(Raw)이 보존되어 있는가

**품질**
 - [ ] 원천 건수와 적재 건수를 대조하는가
 - [ ] 핵심 컬럼의 null·중복·범위를 검사하는가
 - [ ] 검증 실패 시 차단/경고 기준이 정해져 있는가

**거버넌스**
 - [ ] 모든 핵심 테이블에 오너와 설명이 있는가
 - [ ] 지표 정의가 한 곳에 문서화되어 있는가
 - [ ] 개인정보가 마스킹/가명처리되어 있는가
 - [ ] 권한이 최소 범위로 부여되어 있는가

**장애 대응**
 - [ ] 심각도 기준과 담당자 연락 체계가 있는가
 - [ ] 영향 범위를 lineage로 확인할 수 있는가
 - [ ] 장애 후 회고와 재발 방지 조치를 남기는가

## 12. 정리

 - 데이터 운영은 분석의 **앞단 지원 업무가 아니라 신뢰의 토대**다.
 - 핵심 축은 **자동화 · 품질 검증 · 모니터링 · 거버넌스 · 장애 대응**이다.
 - 기업은 규모가 커질수록 **사람의 주의력이 아니라 프로세스와 시스템**으로 품질을 지킨다.
 - 시작은 작게, **가장 아픈 문제 하나부터** 자동화하고 문서화하는 것이다.
